# Box 1 firmware plan (draft - 2026-10-02)

Source of truth for the new Box 1 procedure: **`BOX1_STEPS_FINAL_2026-10-02.json`** (frozen copy of the final export - 30 steps, "Preset 2"). Final verification 2026-10-02: structure clean, every screen within the display limits, and whole-session replays (normal, free retry, abort/resume/confirm, cancel yes/no, refill failure -> bypass -> out of order -> recovery, bypass persisting to the next customer, scented refill, water-sensor splash) all end where they should.
Pins: `RevisedJollyHelmet_Checked.xlsx`. Rules: 5-minute minimum, 15 coins = 5 min (20 s/coin), rating bands 1-5=5 / 6-7=10 / 8-9=15 / 10=20 min, free retry at rating 8+ for 2 min, once.
Goal: **Box 1 fully operational first**, then Box 2, Box 3, ACS 1, ACS 2.

## 1. What exists today vs what is new

| Piece | Today (flashed, working) | Needed for the new Box 1 |
|---|---|---|
| S3A (brain) | 17-state flow, 1 humidifier + UV, -/+ time buttons, 5-bit relay mask sent to A2 | ~23 states, 3 mist modes, rating -> time, free retry, status feed, 12-bit relay mask sent to **A3** |
| A1 (screen/coin/buzzer) | text, timed text, 3 buttons, shapes; 4 ST / 4 TT / 3 BTN / 4 SHP caps; payload <= 199 chars | new widgets: **NR2** rating, **NP** numpad, **PBAR**; tokens `{MINUTE} {SECOND} {STATUS}` |
| A2 (sensors) | still the OLD board: sensors AND relays | sensors only: helmet US, MC ALS + MC SLS US, 2 water sensors, 4 reed doors |
| A3 (relays) | does not exist in firmware (hardware + pin sheet only) | **new sketch**, 12 relays, boot-safe |
| LocalServer | settings for secondsPerCoin / min / max coins | rating bands, min time, coin rate with Second/Minute dropdown, free retry, Maintenance button |
| Shared_Common.h | 8 identical copies | new states, DEVICE_A3, new opcodes/packets (struct sizes must stay pairwise distinct) |

## 2. How the Designer steps map to firmware states

Designer steps that are NOT separate states: START CLEANING (a routing decision), the six CLEANING variants (one CLEANING state + `mistMode` + `isFreeRetry` flags), OUT OF ORDER (A1 draws it itself), MAINTENANCE (entered from the LocalServer).

States: TAPS, CHECKING_ALC, REFILLING_ALC, CHECKING_SCN, REFILLING_SCN, WELCOME, RATE_A, METHOD, TIME_ALLOT, INSERT_COIN, OPEN_A (= today's INSTRUCTIONS), SENSORS_A, CLOSE_A, CLEANING, OPEN_B (= RETRIEVE), SENSORS_B, CLOSE_B, RATE_B, FREE_RETRY, FINISH, ABORT_CONFIRM, CANCEL_CONFIRM, MAINTENANCE, PAUSED_SAFETY (existing). New values are appended - never renumber the old ones.

Session variables inside S3A: `mistMode` (alc/sct/bal), `retryUsed`, `returnState` (for ABORT/CANCEL "return to the step that opened this screen"; the Box 2 firmware already has `returnStateAfterInterrupt`), `requiredCoins`, `ratingA`, `ratingB`.

Relay sets (A3 bits 0-11 = enc, pan, bak, hum1, uv1, hum2, hum3, uv2, drain1, drain2, acs door, coin):
- ALCOHOL SET: UV1 + UV2 + Hum1 + Hum3 (+ Coin when paid); SCENTED SET: UV1 + UV2 + Hum2 + Hum3; BALANCED: UV1 + UV2 + Hum1 + Hum2 + Hum3.
- Coin power ON only in INSERT_COIN and paid CLEANING. Enclosure lock ON (unlocked) only in OPEN_A / OPEN_B. Drain pumps: maintenance only.

The screen message only carries the placeholder `{STATUS}` (8 characters); the status text itself travels to A1 in its own small message.

**Phase 2 - A3 firmware (new) - WRITTEN 2026-10-02, not yet compiled/flashed**
`ESP32_A3\ESP32_A3.ino`: 12 active-LOW relays, every pin driven HIGH before pinMode(OUTPUT); applies `CMD_SET_RELAY_MASK` (turn-offs at once, turn-ons staggered 25 ms); the receive callback only records, loop() alone touches the pins; manual `CMD_SET_RELAY` also accepted for bench use; S3A proof of life = heartbeat (subIndex DEVICE_S3A) or any command to A3; **watchdog (15 s, moved from A2)**: all 12 outputs OFF, except the enclosure lock is held unlocked while A2's last telemetry says door shut + helmet inside (<15 cm), released once the door is confirmed open (2 ticks), solenoid capped at 60 s on / 5 s rest, 3 windows; if A2 is silent too, ONE 15 s unlock window (`UNLOCK_BLIND_WINDOW_MS`, decided by the user 2026-10-02 to protect the solenoid; `UNLOCK_WHEN_A2_UNKNOWN` can switch it off); the old mask is forgotten when orphaned, so a returning S3A must send a fresh mask; broadcasts `A3StatusPacket` every 1 s.

**Phase 3 - A2 rewrite (sensors only) - WRITTEN 2026-10-02, compiles, not yet bench-tested**
`ESP32_A2\ESP32_A2.ino` is now sensing-only; the old relay-carrying A2 is archived as `ESP32_A2\ESP32_A2_LEGACY_pre_A3.ino.txt` (it is still what runs on the customer's box). New packet `A2SensorPacket` (25 bytes, in Shared_Common.h): helmet / MC ALS / MC SLS ultrasonic cm (0 = no echo), 4 door reeds (true = OPEN: enclosure, panel, backdoor, ACS side), 2 water sensors as wet/dry flags PLUS their raw 12-bit readings, rolling `seq`. **The water sensors are ANALOG (user, 2026-10-02)**, so they moved from GPIO5/17 (no ADC) to **GPIO34 (alcohol) / GPIO35 (scented)** - input-only ADC1 pins; the pin sheet (A2 and B2 blocks) was updated and logged. A2 averages 8 readings every 50 ms and decides wet/dry with hysteresis (`WS_WET_ENTER_RAW` / `WS_WET_LEAVE_RAW`) held 500 ms. Sent every 1 s and immediately (>= 100 ms apart) when a door/water sensor changes. Ultrasonics are pinged round-robin 20 ms apart (no cross-talk) and reported as the median of each sensor's last 5 readings; doors debounced 50 ms, water sensors 500 ms. No outputs (except the TRIG pins), no commands, no watchdog. **User decision 2026-10-02: no spare ESP32 for a bench, so A2 + A3 go straight into the customer's box.** To make that work with the S3A / LocalServer / A1 that are flashed there today (they only know the OLD A2: `TelemetryPacket` in, per-relay `CMD_SET_RELAY` to DEVICE_A2 out), both sketches carry a **TEMPORARY LEGACY BRIDGE** (`LEGACY_S3A_BRIDGE 1`, remove in Phase 5): A2 also sends an old-style `TelemetryPacket` (helmet, 3 doors, `relayStates` mirrored from A3's status so the dashboard buttons are truthful, and a FIXED alcohol distance of 4.0 cm because the old S3A's 2..9 cm tank geometry does not fit the new main container - dashboard alcohol % is therefore NOT real; `LEGACY_ALC_MODE 0` passes the real reading); A3 obeys `CMD_SET_RELAY` addressed to DEVICE_A2: 0/1/2 -> enclosure/panel/backdoor lock, 3 (humidifier) -> **all three humidifiers** (`LEGACY_MIST_MASK` = the new design's BALANCED set, because the old mist was the mixed product - user clarified 2026-10-02: Hum 1 = alcohol container, Hum 2 = scented container, Hum 3 = both), 4 (UV) -> UV 1 + UV 2, and switches **COIN POWER by S3A's broadcast state**: ON only in STATE_INSERT_COIN and STATE_CLEANING (the two places the designed steps turn Coin ON - paid cleaning lets the customer add time), OFF in every other state and when S3A's status is older than 3.5 s (user: the acceptor must not take money it did not ask for). A `CMD_SET_RELAY_MASK` from the new S3A switches the bridge off by itself. The old relay A2 must be unplugged; rollback = reflash the old A2 board with `ESP32_A2_LEGACY_pre_A3.ino.txt` (rename to `.ino`) and move the loads back.
Open (needs the user + the real liquids): **calibrate the water sensors**. The thresholds in the sketch (600 wet / 400 dry, `WS_WET_IS_HIGHER` 1) are placeholders; read the raw values on the Serial Monitor dry, in the scented liquid and in the alcohol, then set them. Resistive sensors sense conductivity, so strong isopropyl alcohol may read much lower than water-based liquid - if it barely reacts, a different sensor type (e.g. a float switch) is needed for the alcohol container. Wiring: power the sensors from 3.3 V (not 5 V), optional 100 k pull-down to GND at the pin so a loose wire reads dry.

**Phase 4 - A1 display - WRITTEN 2026-10-02, compiles, not yet tried on the real screen**
`ESP32_A1\ESP32_A1.ino` now understands (everything else, including every old screen, is untouched; at most one of each widget per screen, kept apart from the 4/4/3/4 item arrays):
- `NR2,x,y,w,h,value,textColor,selectedColor,top;bottom` - rating grid, 1-5 over 6-10, same arithmetic as the Designer. A tap only selects (green box); value 0 = none picked. The screen's own button (CONFIRM) sends the rating: **CMD_TOUCH_ACTION now carries param16** = rating on a screen with an NR2 (0 otherwise, so old behaviour is unchanged).
- `NP,x,y,w,h,color,secPerCoin,label[,initialSeconds]` - numpad. Typing, DEL, MM:SS roll-over, 4-digit rollover and the live "N coin(s) needed" line all run on A1; only results leave: `NP_OK` (param16 = seconds, capped 99:59), `NP_BACK`, `NP_CANCEL`. The optional 9th field is the suggested time (S3A will fill it from the customer's rating); the first digit typed replaces a suggestion, DEL edits it. Min/max coin checks stay in S3A (it owns the rules): it answers with a warning screen or a re-rendered numpad.

- Tokens: `{MINUTE}:{SECOND}` (zero-padded, from the synced timer), `{STATUS}`/`{STATUS2}`/`{STATUS3}` (new **CMD_STATUS_LINE**, <= 31 chars, empty text clears), `{TRY}`/`{TRIES}`/`{MAXCOINS}` (new **CMD_SET_TOKEN = 16**, subIndex = TokenId, param16 = value).

- The red debug crosshair is skipped on widget screens (they redraw themselves on every tap).
New tool `ESP32_A1_WIDGET_TEST` (spare ESP32, Wi-Fi `A1_TEST` / `12345678`, http://192.168.4.1): plays the S3A for A1 - sends any of the 46 screens in `a1_screens.h` (the 30 NEW ones + 2 variants + the OLD screens for a regression check), the once-a-second heartbeat/countdown, status lines and counters, and lists every touch action with its value. **Phase 5 - S3A state machine - WRITTEN 2026-10-02, compiles (no warnings), NOT yet run on the box**
`ESP32_S3A\ESP32_S3A.ino` is a full rewrite; the old one is archived as `ESP32_S3A\ESP32_S3A_LEGACY_old_flow.ino.txt` (it is what runs on the customer's box today). Screens are generated from the frozen Designer export into `S3A_Screens.h`.
- **Flow:** the whole 30-step journey (see section 2). One `STATE_CLEANING` + `mistMode` + `cleanFree` instead of six; START CLEANING is a routing function. All logic runs in `loop()` at 1 Hz with 2-tick debouncing (same as before); the radio callback only stores packets and queues commands.
- **Relays:** one 12-bit mask worked out from the state and sent to A3 (re-sent every 2 s). Coin power ON only in INSERT COIN and paid CLEANING (and only while the session is under maxCoins); FREE cleaning has none; UV 1+2 always together; Hum 3 in every mist mode; Hum 1 for alcohol, Hum 2 for scented, both for balanced. TFT hard refresh when the enclosure lock engages is kept.
- **Safety, beyond the Designer:** (1) enclosure solenoid is never energized more than 60 s in a row (5 s rest), in OPEN A/B, the safety pause and Maintenance; (2) the door opening during CLEANING pauses it (UV, mist and coin off; resumes when the door is shut with the helmet in; time and bar kept); (3) if A2 goes silent S3A assumes door OPEN / no helmet, so a cleaning pauses; (4) if A2 or A3 is silent when a customer taps, the box goes OUT OF ORDER instead of taking coins it cannot serve.
- **Rating/time/coins:** rating A -> suggested time (bands, never under the minimum) fills the numpad; S3A validates NP_OK (minimum, maxCoins) and answers with a small warning screen (OK returns to the numpad with the typed time); coin rate "N coins = X sec/min"; coins beyond the price are discarded; extra coins during paid cleaning add time and make A1 repaint the bar's total. Pulses are ignored when the acceptor should be off.
- **Containers:** CHECKING A/S use the Main Container ultrasonics against Low (and High for "refilled") distances, backed up by the analog water sensors judged HERE from A2's raw readings with the calibration settings. `levelChecksOn` defaults to OFF until the four distances are measured. REFILLING counts 10 tries x 10 s with `{TRY}/{TRIES}`; the request to the ACS is a setting (`acsRequests`, default OFF - Box 1's ACS is leaking and its old firmware pumps on any delivery request); after the last try -> bypass ON (saved in NVS) -> OUT OF ORDER; it clears itself and bypass switches off when everything is back. 
- **Dynamic settings** (NVS; LocalServer edits them with CMD_SET_CONFIG subIndex 1 = RULES 20 numbers, 2 = LEVELS 14 numbers; S3A rebroadcasts both every 2 s as CMD_SET_CONFIG target 0). The USB serial console does the same today: `help`, `cfg`, `set <name> <value>`, `bypass`, `reset`.
- **Maintenance:** `CMD_SET_MAINTENANCE` (state 1/0) from LocalServer, accepted only from the idle/out-of-order screen; in it `CMD_SET_RELAY_MASK` to S3A switches relays by hand.
- **Flow revision 2 (2026-10-02, user fixed SENSORS B after his boss got stuck there): `BOX1_STEPS_2026-10-02_v2.json`, 32 steps.** Changes vs. the first export: two new steps HELMET NOTICE A ("HELMET / NO / DETECTED") and HELMET NOTICE B ("HELMET / DETECTED"), 2 s each, then back to OPEN A / OPEN B; SENSORS A and CLOSE DOOR A send "door shut, no helmet" to NOTICE A (was straight back to OPEN A); SENSORS B / CLOSE DOOR B send "door shut, helmet still in" to NOTICE B; SENSORS B's first branch is now [helmetAbsent AND doorClosed] -> CLOSE DOOR B (was [NOT helmetPresent AND doorOpen]). The old SENSORS B had no branch for "helmet out and door already shut", so a helmet taken out + door closed quickly waited forever. ## 4. Risks to watch
- Screen payload <= 199 chars; A1 item caps (4 ST / 4 TT / 3 BTN / 4 SHP); each text line <= 31 characters once filled in (ST text[32], TT templateText[32] + lastRendered[32]); button label and action <= 15. All silently truncated by the firmware, so the Designer now checks every one of them.
- ESP-NOW packets are told apart by size only: every new struct must have a unique size.
- The TFT white screen can still happen on lock engage (the hard refresh recovers it; decoupling capacitors are the real fix).
- ESP-NOW + analog pins: use ADC1 pins only (32-39) for any analog sensor.
- Relay boot glitches: avoid GPIO 0/1/2/3/5/12/14/15 for relays (A3/B3 already moved).

## 5. Decisions (user, 2026-10-02) and what is still open

**Decided**
1. **Refill failure -> "last legs" bypass.** If the ACS cannot be contacted through S3 (no ACS telemetry for ~15 s) or a refill can never finish, S3A skips every refill check and keeps serving with what is in the containers. Before each customer it checks whether there is enough to run; if not, it goes OUT OF ORDER (screen sent by S3A - different from A1's own offline OUT OF ORDER) or MAINTENANCE.
2. **UV 1 and UV 2 are one logical "UV"** - always switched together while cleaning (inside and outside of the helmet). In S3A treat them as a single `uvOn` that sets both relay bits.
3. **Ratings are saved for stats.** The LocalServer (an ESP32 with its own Wi-Fi access point and web dashboard, no internet) counts as the "web" side for now. Extend the session record from {duration, coins} to also hold ratingA, ratingB (0 = not rated), mist mode, free retry used, and outcome (finished / aborted / cancelled). Totals stay in NVS; keep the per-session history in a LittleFS CSV with an "Export CSV" button so a future internet web app can import it. There is no real-time clock offline - either store a session number, or let the dashboard send the browser's clock when it is opened.

4. **"Enough resources" = the container is above its LOW line.** Critically low and low are treated the same: not enough. (A water sensor that is wet counts as "not low", because it backs up a splashed ultrasonic.)
5. **Humidifier 3 (Both) draws from BOTH containers and runs in every mist mode**, so every session needs both containers to have enough. That makes the check independent of the mode: if either container is not "enough" the box cannot serve anyone, so there is no "choose another mode" screen. The check therefore lives in the existing CHECKING steps at the very start (the customer finds out before rating or paying), and the Designer has two conditions for it: "Alcohol/Scented Container Has Enough (not Low, or water sensor wet)".
   Flow: CHECKING -> not enough and bypass ON -> OUT OF ORDER; not enough and bypass OFF -> REFILLING (10 tries, 10 s apart) -> refilled -> CHECKING again, or gave up -> bypass ON -> OUT OF ORDER. OUT OF ORDER -> both containers enough again -> bypass OFF -> TAPS (and the refill system is retried on the next customer).
6. **Refill retry rule:** ask the refill system (ACS) again every **10 seconds, up to 10 tries**, with a visible counter ("Refilling... 3/10", like an internet reconnect). After the 10th try with no answer (or no progress) the box **gives up** and turns on **Refill bypass**, which stays on for every following customer (skips every refill check) until the system answers again.
7. **When resources run out:** OUT OF ORDER for customers (sent by S3A) plus a LocalServer dashboard alert; MAINTENANCE only when the operator switches it on. OUT OF ORDER clears itself when the levels are OK again.

8. **S3A itself lost mid-session (existing behavior, kept).** The steps all run on S3A, so nothing can continue them. After 15 s of silence A1 draws its own blinking OUT OF ORDER and clears it when S3A is heard again (`ESP32_A1.ino` `tickOutOfOrder`); the relay node's orphan watchdog forces Mist and UV OFF and, if the door is closed with a helmet inside, unlocks the enclosure so nobody is trapped, then releases the lock once the door is open (`ESP32_A2.ino`, today the board that holds the relays). S3A's session lives in RAM, so after it restarts it begins again at TAPS: the paid time is lost (no refunds, per policy). This is a different OUT OF ORDER from the Designer's step, which S3A sends itself when the containers run out.
   **Confirmed by the user (2026-10-02): unlock the door after 15 s when S3A is lost and a helmet is trapped inside.**
   **Carry into the new hardware:** the relay watchdog moves to **A3**, but A3 has no sensors - it must listen to A2's broadcast door/helmet readings (or unlock whenever S3A is silent), switch **all** mist, UV and **coin power** OFF after 15 s, and unlock only if A2 last reported a helmet inside.

**Firmware implications:** S3A keeps `refillTries` (0-10, one per 10 s), a `refillBypass` flag (RAM, recomputed after a reboot from ACS telemetry), and sends `{TRY}`/`{TRIES}` to A1 as plain numbers; A1's `interpolateTemplate` must learn `{TRY}`, `{TRIES}`, `{MINUTE}`, `{SECOND}`, `{STATUS*}`. The LocalServer needs an "ACS not responding / out of liquid" alert.

**Still open**
- The old `AUTO_CALL` (S3A asks the ACS to deliver alcohol) belongs to the old single-tank ACS design - it must be redefined once ACS 1/ACS 2 are final.
